# 本番DB接続の再利用

本番では、各 Puma ワーカーに最低2本の DB 接続を常に用意しておく（`min_connections: 2`）。2本を超えて作った接続は、30分使われなければ閉じる（`idle_timeout: 1800`）。

## なぜ必要か

- 本番 DB（Aiven for PostgreSQL、DigitalOcean sfo）は Heroku（米国東部）から遠い。新しい接続を作るのに約1.5秒かかる（TLS・認証に加え、Rails が接続ごとに流す設定と型の読み込みの SQL が約11往復）。
- アクセスが少ないため、接続を必要なときだけ作る設定（2026-11-22 までの `min_connections: 0`）では接続がすぐ空になる。利用者のリクエストが、ときどきこの1.5秒を待っていた（PostgreSQL 切替直後の計測で、接続を作ったリクエストだけ 1.6〜2.3 秒、2回目以降は MySQL のときと同じ 90〜270ms）。

## 仕組み

- Puma の各ワーカーは、起動時に接続プールを使用中にしてから1本つなぐ（`config/puma.rb` の `before_worker_boot` から `lib/database_warm_up.rb`）。起動の瞬間に DB につながらなくても、プールは使用中のまま失敗した接続だけ捨てるので、DB が戻れば定期処理（約20秒ごと）が2本作ってつなぐ。ただし DB が止まっている間に定期処理がつなごうとして失敗した接続は、Rails が裏ではつなぎ直さない。その接続は、最初に使うリクエストのときにつなぐ（そのリクエストだけ約1.5秒かかる）。つながらなかったときは、原因（例外の種類とメッセージ）をログに出し、Sentry にも送る。
- DB につながらないとき、各ワーカーの起動は約20秒延びる（`connect_timeout` 10秒 × 再試行1回）。Puma のワーカー起動の制限（60秒）には収まるので、起動を繰り返すことはない。
- 残りは Rails の定期処理（reaper、約20秒ごと）が裏で作り、2本を保つ。使われていない接続にも定期的に問い合わせて生かしておく（keepalive、既定600秒）。そのため、途中の機器に接続を切られにくい。
- 接続が切られていた場合（DB の再起動・メンテナンスなど）は、次にその接続を使うときか、次の keepalive（最大で約10分後）で気づいて作り直す。20秒ごとの定期処理では作り直さないので、DB の再起動から約10分は、ときどき接続の準備（約1.5秒）を待つリクエストがある。
- 上限は各ワーカー `RAILS_MAX_THREADS` 本（`max_connections`）。現在の2ワーカー・5スレッドでは、常時4本、最大10本。
- Aiven 無料プランの接続上限は20本で、うち3本は管理用に予約されている。アプリなどが使えるのは17本。
  - 常時分: デプロイや再起動で新旧の dyno が重なっても8本。月1回のバックアップ（`gatareview_backup`、最大2本）と `heroku run` などの one-off dyno（runner・console は1本。migrate はロック用に別の接続を使うので2本）を足しても12本で収まる。
  - 混んだとき: 1つの dyno で最大10本まで増える。混んだ dyno が2つ重なる（デプロイ中に高負荷が続くなど）と20本になり、17本を超える。超えた分の接続は `too many clients` で失敗し、そのリクエストは 500 になる。これは `min_connections` を入れる前からある上限で、今のアクセス量では起きにくい。アクセスが増えたら `RAILS_MAX_THREADS` を3〜4に下げるか、DB のプランを上げる。
- 本数は環境変数 `DB_MIN_CONNECTIONS` で変えられる（既定2）。数字以外を入れると0本（用意しない）として扱われるので、整数で設定する。
- `sslmode: verify-full`、CA の検証、最小権限の実行ユーザーは変えない。

## 検証

`spec/services/database_connection_reuse_spec.rb` では、隔離したDBで実際に接続し、次を確認する: 最低2本の準備（起動の瞬間に DB につながらなかった場合も、あとで2本そろうこと）、Puma の起動時にこの処理が呼ばれること、未使用時間を再現した10分後の再利用、30分超過後に最低本数を残して余分だけを閉じること、切断済み接続からの回復。試験用のトランザクションによる接続の固定は無効にしている。

Issue: https://github.com/yu-yaba/gatareview-back/issues/55

（以下は MySQL 時代に `idle_timeout` を5分から30分にしたときの記録）

比較試験では、同じデータと6回の読み取りを使い、10分の待機を再現した。TCP/TLSとSQLは実通信し、透過中継でパケットの内容を保存せずバイト数だけを数えた。変更後には保持した接続へのkeepaliveの通信も含めた。

| 項目 | 変更前 | 変更後 |
| --- | ---: | ---: |
| TCP/TLS接続数 | 6 | 1 |
| 双方向の通信量 | 38,678 bytes | 9,826 bytes |
| 接続取得・読み取りの中央値 | 48.56 ms | 1.07 ms |

待機時間の判定を再現したローカル試験の結果であり、本番のネットワーク遅延や月間の削減量を示す値ではない。
